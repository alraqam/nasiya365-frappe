# Поиск по IMEI — дизайн (Фаза 1)

- **Дата:** 2026-07-25
- **Ветка:** `feat/searching-panel`
- **Статус:** утверждён дизайн, спецификация на вычитке
- **Прототип панели:** https://claude.ai/code/artifact/ea4b0b1c-a1cf-441e-90a8-495f6c6616d0

## 1. Проблема

Мерчант жалуется: товар (телефон) невозможно найти по IMEI — поиск срабатывает
только по номеру документа (ID). У Installment Plan и Sales Order в `search_fields`
перечислены только `customer / customer_name`, поэтому ввод IMEI ничего не находит.

## 2. Модель данных (как IMEI живёт в системе)

Один физический телефон = один IMEI. След остаётся в:

| Объект | Где IMEI | Тип поля |
|---|---|---|
| `Installment Plan` | `imei` | **верхнеуровневое** поле (1 план = 1 телефон) |
| `Sales Order` | `sales_order_item.imei` | дочерняя таблица |
| `Stock Entry` | `stock_entry_item.imei` | дочерняя таблица |
| `Trade In` | `imei` | поле |

Ключевое следствие: `search_fields` умеет искать только по полям **самого**
доктайпа, не по дочерним таблицам. Поэтому по рассрочке поиск чинится тривиально,
а по продажам/складу (imei в дочерней) — требует отдельного запроса.

## 3. Бизнес-модель поиска

### Сценарии (кто и зачем ищет)

| # | Ситуация | Что нужно узнать | Частота |
|---|---|---|---|
| S1 | Клиент пришёл платить / с проблемой, телефон в руках | Чей план, статус, остаток | ежедневно |
| S2 | Гарантия / возврат / сервис | Наш ли телефон, когда/кому продан | средняя |
| S3 | Выкуп / trade-in | Проходил ли IMEI через нас раньше | средняя |
| S4 | Проверка склада | Пришёл ли IMEI, в наличии или продан | низкая |
| S5 | Аудит / бухгалтерия | Проследить конкретный юнит | редкая |

### Разделы и фазы

Решение: **не** делать единый универсальный поиск в одном месте. Встраиваем IMEI
в естественные разделы, где уже есть фильтрация.

Аудит существующих фильтров показал: финансовые отчёты
(`profit_and_loss_summary`, `shareholder_distribution`, `suppliers_payable`,
`cashbox_income_by_period`) фильтруют по дате/филиалу — IMEI там не нужен.
Места, связанные с телефонами/планами:

| Фаза | Раздел | Сценарии | Механизм |
|---|---|---|---|
| **1** | Список рассрочек + выпадашка выбора плана | S1 | `imei` в `search_fields` |
| **1** | Глобальный поиск (по рассрочкам) | S1 | тот же `search_fields` |
| **1** | Панель BNPL | S1 | поле «Найти по IMEI» → мини-карточки |
| **1** | Страница сбора просрочки (`overdue_collector`) | S1 | «Поиск клиента» → «клиент или IMEI» |
| **1** | Отчёт «Продажи» (`sales_report`) | S2/S4 | новый фильтр IMEI + колонка IMEI |
| **2** | Список продаж (Sales Order), Склад, Trade-in, отчёт «Сборы» | S2–S5 | отдельно, imei в дочерних таблицах |

**Эта спецификация покрывает Фазу 1 — 5 точек входа (см. §5).**

## 4. Зафиксированные решения по UX

- **Режим поиска:** частичное совпадение по любой части IMEI (`LIKE %...%`).
- **Минимум:** 3 цифры (короче — подсказка, запрос не шлём).
- **Санитизация ввода:** оставляем только цифры (буквы/пробелы игнорируются).
- **Результат на панели BNPL:** мини-карточка (клиент · статус-пилюля · номер
  плана · товар+IMEI с подсветкой совпадения · остаток) + кнопки **«Открыть план»**
  и **«Принять платёж»**.
- **Страница сбора просрочки:** существующая строка «Поиск клиента» ищет и по
  клиенту, и по IMEI (одно поле). Placeholder → «Поиск: клиент или IMEI».
- **Отчёт «Продажи»:** отдельный необязательный фильтр «IMEI»; в результат
  добавляется колонка IMEI, чтобы видеть совпадение.

## 5. Дизайн реализации (Фаза 1)

### Часть 1 — Метаданные (рассрочки)

**Файл:** `nasiya365/nasiya365/doctype/installment_plan/installment_plan.json`

```diff
- "search_fields": "customer,customer_name",
+ "search_fields": "customer,customer_name,imei",
```

- Покрывает: список рассрочек, выпадашку выбора плана (напр. при приёме платежа),
  глобальную строку (awesomebar) — везде, где Frappe использует `search_fields`.
- `ALTER TABLE` нет: поле `imei` уже существует. Индекс не добавляем — частичному
  поиску (`LIKE %x%`) ведущий индекс не помогает, таблица небольшая.
- Требует `bench migrate` (синхронизация меты доктайпа).

### Часть 2 — Backend API (панель BNPL)

**Файл:** `nasiya365/api/bnpl_dashboard.py` — новый whitelisted-метод.

```
search_plans_by_imei(imei, limit=20)
```

Логика:
1. Обрезать пробелы, оставить только цифры.
2. Если длина < 3 → вернуть `[]` (без запроса к БД).
3. Экранировать `%` и `_` в терме (LIKE-безопасность).
4. SQL по `tabInstallment Plan ip`:
   `WHERE ip.imei LIKE %term%` + `_user_branch_clause("ip")` (тот же фильтр по
   филиалам, что во всём модуле).
5. Вернуть поля: `name, customer, customer_name, status, remaining_balance,
   product_name, imei`. `ORDER BY modified DESC`, `LIMIT` из параметра
   (через существующий `_safe_limit`).

Свойства: только чтение, права/филиалы уважаются.

### Часть 3 — UI панели

**Файлы:** `bnpl_control_center.js`, `public/css/bnpl_control_center.css`

- Новый блок «Найти по IMEI» под sticky CTA-строкой.
- Поле ввода: `inputmode="numeric"`, placeholder-пример, кнопка очистки.
- Ввод с debounce ~300 мс → вызов `search_plans_by_imei`.
- Рендер мини-карточек (см. §4). Состояния: пусто / «≥3 цифры» / «не найдено».
- Кнопки:
  - «Открыть план» → `frappe.set_route("Form", "Installment Plan", name)`.
  - «Принять платёж» → переиспользуем существующий
    `openPaymentDialog({ customer, installment_plan: name, amount_due: remaining_balance })`.
- Стили — в CSS панели, в том же визуальном языке (переменные `--card-bg`,
  `--border-color`, акцент, радиусы 14/10px).

### Часть 4 — Страница сбора просрочки

**Файлы:** `nasiya365/api/bnpl_dashboard.py`,
`nasiya365/nasiya365/page/overdue_collector/overdue_collector.js`

- В `get_due_today_list` и `get_overdue_list` добавить в SELECT `ip.imei AS imei`
  (обе строятся на `tabInstallment Plan ip`, поле верхнеуровневое — добавка
  тривиальна, филиалы уже фильтруются).
- В JS клиентский фильтр (сейчас по `customer_name/customer`) расширить: совпадение
  также по `imei` (цифры терма ⊂ imei). Placeholder → «Поиск: клиент или IMEI».
- Поиск остаётся клиентским по уже загруженным строкам — новых запросов не добавляем.

### Часть 5 — Отчёт «Продажи» (`sales_report`)

**Файлы:** `nasiya365/nasiya365/report/sales_report/sales_report.js`,
`sales_report.py`

Важно: сейчас `ip.imei` в отчёте используется только внутри (расчёт COGS), как
колонка **не выводится**; наличная ветка (Sales Order) imei вообще не тянет.

- `.js`: добавить необязательный фильтр `imei` (Data).
- `.py`:
  - Ветка «Рассрочка»: при заданном фильтре — `AND ip.imei LIKE %imei%`.
  - Ветка «Наличные»: `AND EXISTS (SELECT 1 FROM tabSales Order Item soi
    WHERE soi.parent = so.name AND soi.imei LIKE %imei%)`.
  - Добавить в вывод колонку `imei`: для рассрочки — `ip.imei`; для наличных —
    дотянуть imei из `Sales Order Item` (рядом с тем, как уже берётся `product_name`).
  - Экранировать `%_` в терме.

## 6. Тестирование

- **Python-тест** на `search_plans_by_imei`:
  - частичное совпадение находит план;
  - чужой филиал не виден (ограничение по филиалам);
  - терм < 3 символов → `[]`;
  - LIKE-метасимволы в терме не ломают запрос.
- **Python-тест** на `sales_report` с фильтром `imei`: находит и рассрочку
  (по `ip.imei`), и наличную продажу (по `sales_order_item.imei`).
- **Ограничение:** на сайте выключены тесты (`allow_tests`). Варианты прогона:
  (а) временно включить в dev — FrappeTestCase откатывает свои записи;
  (б) проверить логику через `bench console`. **Открытое решение (см. §9).**
- **JS/панель/страница просрочки** — проверка вручную в браузере (чистая вкладка).

## 7. Деплой

- Часть 1 требует `bench migrate` — уже автоматизирован в `docker-compose.prod.yml`.
- Части 2–5 (Python + JS) отдаются из исходников; нужен `bench restart` для
  подхвата новых whitelisted-полей/методов и очистка кэша браузера для JS.

## 8. Вне области (Фаза 2)

- **Склад** (`Stock Entry`) и **Trade-in** по IMEI, каждый в своём разделе.
- Фильтр IMEI в отчёте **«Сборы/просрочка»** (`collections_and_overdue`).
