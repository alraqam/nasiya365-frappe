# P&L: метод «Возмещение затрат» (cost recovery) + новый вид отчёта

**Дата:** 2026-07-28
**Статус:** дизайн утверждён пользователем, ожидает финального ревью спека
**Область:** отчёт «Прибыль и убытки» (`profit_and_loss_summary`) и движок `nasiya365/api/profit.py`

---

## 1. Проблема

Мерчант пожаловался на строку «Рассрочка — выручка (товар)» в P&L: сегодня она показывает
$450, но это не выручка от продажи товара — это сумма **собранных за день денег** по РАЗНЫМ
сделкам (первый взнос $350 по сегодняшней продаже + очередной платёж $100 по июньской),
причём внутри ещё сидят проценты.

Корень: `profit_method` в Merchant Settings не задан → движок по умолчанию считает по **кассе**
(пропорциональный метод): признаёт долю прибыли с каждого платежа. Это законный метод и
арифметически он сходится (за срок сделки признаётся вся прибыль, без двойного счёта, прибыль
акционеров не искажена), но он **не совпадает с тем, как мерчант понимает прибыль**.

**Важно (проверено на живых данных прода):** валютного бага НЕТ. Все суммы на проде уже в USD
(Installment Plan, Sales Order, Payment Transaction, Stock Entry Item — все в долларах;
расходов на проде 0). Подпись «Сумма (USD)» корректна. Прежняя диагностика «числа в сумах»
относилась к тестовым данным dev, не к проду.

## 2. Решение (утверждено)

Ввести **третий метод признания — «Возмещение затрат» (cost recovery), вариант A**, по каждой
сделке отдельно:

- Прибыль по сделке = **$0**, пока собранные по ней деньги не покроют её себестоимость (COGS).
- Как только собрано сверх COGS — всё превышение признаётся прибылью (и наценка, и проценты).
- Наценка $30 и проценты $90 признаются **вместе, после возврата затрат** (пользователь выбрал
  вариант A, а не «наценка сразу при продаже»).

Почему для этого бизнеса: BNPL с реальным риском невозврата; мерчант фронтит живой кэш;
прибыль делится акционерам → консервативный метод защищает от переплаты дивидендов деньгами,
которые ещё не собраны.

## 3. Точный алгоритм

### Обозначения (на сделку)
- `COGS` — себестоимость проданного телефона (существующий `_cogs_for_sale_item`, лот-матчинг по IMEI).
- `margin = principal_amount − COGS` (для рассрочки) либо `total_amount − COGS` (для наличной продажи).
- `interest = total_interest` (для наличных = 0).
- `total_profit = margin + interest`.
- `collected_through(d)` = Σ `amount` завершённых Payment Transaction по сделке с `payment_date ≤ d`.
- `recognized(d) = max(0, collected_through(d) − COGS)`
  (кап сверху не нужен: `collected ≤ total_amount = COGS + total_profit`).

### Признанная прибыль за период `[from, to]`
```
period_recognized = recognized(to) − recognized(from − 1 день)
```
Только сделки, у которых есть хотя бы один завершённый платёж внутри `[from, to]`, могут дать
ненулевую признанную прибыль (иначе `recognized(to) == recognized(from−1)`), поэтому перебираем
именно их.

### Разбивка признанной прибыли на маржу/проценты (пропорционально)
```
margin_frac = margin / total_profit   (если total_profit > 0, иначе 0)
recognized_margin   += period_recognized × margin_frac
recognized_interest += period_recognized × (1 − margin_frac)
```
Это сохраняет работоспособность строк «Маржа», «Процентный доход» и настройки `profit_basis`
(Только маржа / Валовая / Чистая).

### Наличные продажи
Та же формула с `interest = 0`. Продажа, оплаченная целиком и сразу (платёж ≥ COGS), признаёт
маржу в тот же день. Платежи наличной продажи — это Payment Transaction c
`reference_doctype = 'Sales Order'` (как в текущем `_compute_cash`).

### Права и фильтры
Ветвление по филиалам и права пользователя берём из существующих хелперов
(`_user_branches`, `_sales_order_user_clause`, ветка Sales Order → branch), без изменений.

## 4. Два раздела отчёта (разные популяции — это нормально)

- **Раздел 1 «Продажи за период»** — по факту ПРОДАЖИ (accrual-взгляд): что продали в периоде и
  какая заложена экономика. Числа = результат существующего `_compute_accrual`
  (Σ цена продажи, Σ себестоимость, Σ маржа, Σ потенциальные проценты). Справочно, «потенциал».
- **Раздел 2 «Признано за период»** — по факту СБОРА денег (cost recovery): сколько реально
  заработано. Новый `_compute_cost_recovery`.

Разделы намеренно про разное (продажи периода vs сборы периода) и **не обязаны сходиться между
собой** арифметически — это разные вопросы. Подписи должны это ясно передавать.

## 5. Новый вид отчёта (надмножество; сохраняем разбивку наличные/рассрочка)

```
РАЗДЕЛ 1. Продажи за период (справочно, по факту продажи)
  Наличные — продажа .................  Σ
  Наличные — себестоимость (приход) ..  −Σ
  Наличные — маржа ...................  Σ
  Рассрочка — продажа ................  Σ        ← бывшая строка-«врунья», теперь честная
  Рассрочка — себестоимость (приход) .  −Σ
  Рассрочка — маржа ..................  Σ
  Итого маржа товара .................  Σ
  Процентный доход (потенциальный) ...  Σ
  Потенциальная прибыль сделок .......  Σ        ← пока НЕ признана

РАЗДЕЛ 2. Признано за период (возмещение затрат, по факту сбора)
  Собрано денег ......................  Σ
  Возмещение себестоимости ...........  −Σ
  Признанная прибыль .................  Σ
    в т.ч. маржа / проценты ..........  Σ / Σ
  − Операционные расходы .............  −Σ
  ЧИСТАЯ ПРИБЫЛЬ (признанная) ........  Σ
```

Детализация по каждому телефону (приход/продажа/маржа на сделку) остаётся в отчёте «Продажи» —
не дублируем.

### Куда делись текущие 11 строк (ничего не теряется)
| Текущая строка | Куда |
|---|---|
| Наличные — выручка / себестоимость / маржа | Раздел 1 (те же, «выручка» → «продажа») |
| Рассрочка — выручка (товар) | Раздел 1 → «Рассрочка — продажа» (исправлено) |
| Рассрочка — себестоимость / маржа | Раздел 1 |
| Итого маржа с товаров | Раздел 1 → «Итого маржа товара» |
| Процентный доход | Раздел 1 (потенциальный) + Раздел 2 (признанный) |
| Валовая прибыль | делится: Раздел 1 «потенциальная» + Раздел 2 «признанная» |
| Операционные расходы | Раздел 2 |
| ЧИСТАЯ ПРИБЫЛЬ | Раздел 2 «ЧИСТАЯ ПРИБЫЛЬ (признанная)» |

## 6. Что меняем и что НЕ трогаем

**Добавляем:**
- `nasiya365/api/profit.py`: функция `_compute_cost_recovery(from, to, branch)`; ветка в
  `compute_profit`, когда `profit_method` == «Возмещение затрат».
- Merchant Settings: новый вариант в `profit_method` — «Возмещение затрат»; ставим его мерчанту.
- `profit_and_loss_summary.py`: секционный вид, когда метод = cost recovery.

**НЕ трогаем:**
- `_cogs_for_sale_item` и вся логика себестоимости/лот-матчинга.
- Методы `_compute_cash`, `_compute_accrual` — работают как прежде (Раздел 1 переиспользует accrual).
- Права по филиалам, расходы, отчёт «Продажи».
- Данные: миграций нет, отчёт только читает.

**Побочный эффект (ожидаемый, подтверждён пользователем):** отчёт «Распределение по акционерам»
берёт `net_profit` из того же движка → будет считать от новой признанной прибыли.

## 7. Безопасность

1. P&L — **read-only**, в базу не пишет. Данные испортить нельзя; худший случай — неверное число.
2. **Добавляем метод, не заменяем.** Возврат к «касса»/«начисление» — один клик в настройке, мгновенно.
3. Никакие деньги не двигаются автоматически (отчёт по акционерам тоже только показывает).
4. Нет удаления кода, нет миграций.

## 8. Тесты (обязательно)

Юнит-тесты `_compute_cost_recovery` (и разбивки маржа/проценты):
1. Взнос < COGS → признано $0.
2. Собрано ровно = COGS → $0.
3. Сбор пересекает COGS внутри периода → признано = превышение над COGS в этом периоде.
4. Платежи по разные стороны границы периода → признаётся только внутрипериодный прирост.
5. Полный сбор сделки → признаны вся маржа и все проценты (сумма = total_profit), разбивка верна.
6. Наличная продажа, оплаченная целиком (≥ COGS) → маржа признана в тот же день.
7. COGS = 0 (нет совпадения по IMEI) → признано = всё собранное (маржа = principal).
8. Права/филиалы: пользователь видит только свои филиалы (как в текущих методах).

Плюс проверка на живых данных прода в браузере: «касса» даёт то же, что раньше; новый метод — то,
что задумано.

## 9. Вне области (отдельные задачи)

- **Баланс / чистые активы** (стартовый капитал $30K, касса, склад, дебиторка, долг поставщикам)
  — отдельная будущая задача; здесь не делаем. Именно она отвечает «в плюсе ли бизнес в целом».
- Пересчёт исторических периодов, изменение существующих методов — не входит.
- Валютная нормализация — не требуется (данные уже в USD).
